# Архитектура

## Слои

```
loaders  →  chunking  →  models (Ollama)  →  store (SQLite)
                                                  │
cli / api  →  engine  →  retrieval (BM25 + векторы + RRF)  →  generation  →  LLM
                              │
                         evaluation
```

`engine.py` единственная точка входа для интерфейсов: командная строка, HTTP API и тесты работают через один и тот же объект. Модели подключаются через два протокола, `Embedder` и `ChatModel`, поэтому в тестах вместо Ollama подставляются детерминированные заглушки

## Индекс

Один файл SQLite с тремя таблицами

| Таблица | Что хранит |
|---|---|
| `documents` | путь, имя, SHA-256 и размер файла, время индексации |
| `chunks` | текст фрагмента, его порядковый номер, место в документе и вектор в виде BLOB `float32` |
| `meta` | версия схемы, имя модели эмбеддингов и размерность векторов |

Замена документа идёт в одной транзакции: старые фрагменты удаляются каскадно, новые записываются целиком. Если индексация прервётся на середине, в индексе останется прежняя версия файла, а не её половина

При первом поиске фрагменты и матрица векторов поднимаются в память, там же строится BM25. Перед каждым поиском сверяется версия данных: собственный счётчик записей и `PRAGMA data_version`, который SQLite увеличивает, когда базу изменил другой процесс. Поэтому запущенный веб-сервер подхватывает результат `archivarius index` без перезапуска, а при неизменном индексе ничего не перечитывает

## Нарезка

Текст делится на абзацы. Абзац длиннее `chunk_size` делится на предложения, слишком длинное предложение на слова. Затем единицы жадно собираются во фрагменты, а перекрытие набирается из целых единиц с конца предыдущего фрагмента, чтобы мысль на стыке не резалась пополам

Фрагмент не выходит за границу сегмента, то есть страницы PDF или раздела Markdown. Благодаря этому ссылка в ответе всегда указывает на одно конкретное место

## Поиск

**BM25** написан с нуля на инвертированном индексе. Токенизация приводит слова к основе стеммером Snowball для русского и английского, убирает стоп-слова и не различает «е» и «ё». Распространённые реализации BM25 принимают уже готовые токены, так что русскую морфологию всё равно пришлось бы решать отдельно

**Векторный поиск** считает косинусную близость полным перебором: векторы нормализованы, так что это одно матричное умножение. Для личных и командных коллекций до сотен тысяч фрагментов это миллисекунды, а отдельная векторная база не нужна

**Слияние** идёт методом Reciprocal Rank Fusion: `score = Σ 1 / (k + rank)`, `k = 60`. Он работает с местами в списках, а не с оценками, поэтому не требует подгонять шкалы BM25 и косинусной близости под каждый корпус. Каждый метод отдаёт по `candidate_pool` кандидатов, после слияния остаются `top_k`. Места фрагмента в обоих списках сохраняются в выдаче и видны в веб-интерфейсе

Пул по умолчанию 10, а не 30. RRF поощряет согласие методов, и при длинных списках фрагмент на средних местах в обоих списках обходит фрагмент, который один метод уверенно поставил первым. На оценочном корпусе пул 10 поднял Hit@5 гибрида с 0.941 до 0.980, а уменьшение `rrf_k` до 10 почти ничего не дало (подробности в README)

**Разнообразие источников.** Из одного документа в выдачу попадает не больше `max_chunks_per_doc` фрагментов, по умолчанию два. Без этого длинная статья занимает все места, и на вопрос, который сравнивает две темы, модель получает материал только по одной из них. Ограничение действует только на итоговую выдачу, а не на кандидатов: в проверке вариант с ограничением кандидатов до слияния снизил Hit@5 гибрида с 0.980 до 0.941. Несколько сильных фрагментов одной статьи сами по себе сигнал, что она релевантна, и срезать его до слияния вредно

## Генерация

Модель получает системную инструкцию отвечать только по фрагментам и ставить ссылки `[n]`. Сопоставлять сведения из разных фрагментов разрешено явно: в первой версии промпта небольшая модель отказывалась отвечать на вопросы-сравнения, потому что ни в одном фрагменте не было готовой фразы с ответом. «Нет ответа» допускается только когда во фрагментах нет ничего по теме, а на неполный ответ модель отвечает тем, что есть, и говорит, чего не хватает. Номера ссылок извлекаются из текста и сверяются с числом источников, несуществующие отбрасываются

Модели с режимом рассуждений выводят перед ответом блок `<think>`. Таких моделей два вида, и обрабатываются они по-разному:

- гибридные, например `qwen3:8b` и `qwen3:14b`: рассуждения отключаются параметром `think: false` и директивой `/no_think` в запросе, модель сразу пишет ответ
- рассуждающие всегда, например `qwen3:4b`, который в Ollama указывает на версию Thinking-2507: отключить рассуждения нельзя, шаблон чата сам открывает блок, и модель присылает только закрывающий тег

Что это за модель, программа узнаёт у Ollama через `/api/show`. Для рассуждающих моделей потоковый ответ придерживается до закрывающего тега, для остальных только первые 300 символов, на случай если блок всё же придёт. Теги могут быть разорваны между токенами, поэтому фильтр работает с буфером, а не с отдельными токенами

## Подключение к Ollama

Запросы к локальной Ollama идут мимо системного прокси. Иначе при включённом VPN или корпоративном прокси запрос на `127.0.0.1` уходит наружу и не возвращается. Адрес по умолчанию `127.0.0.1`, а не `localhost`: в Windows `localhost` может сначала разрешиться в IPv6, а Ollama слушает только IPv4. Ожидание ответа ограничено 600 секундами, потому что первый запрос включает загрузку модели в память

## Оценка

Релевантность размечается на уровне документов. Поиск возвращает фрагменты, из них собирается список уникальных документов в порядке первого появления, и уже по нему считаются Hit@k, Recall@k, MRR@k и nDCG@k. Так один и тот же набор вопросов подходит для сравнения разных размеров фрагментов и разных моделей эмбеддингов

## Ограничения

- сканы PDF без текстового слоя не распознаются, нужен предварительный OCR
- полный перебор векторов рассчитан на объёмы до сотен тысяч фрагментов, дальше понадобится приближённый индекс
- качество ответа ограничено локальной моделью: модели на 4–8 млрд параметров чаще упускают детали, разбросанные по нескольким фрагментам
